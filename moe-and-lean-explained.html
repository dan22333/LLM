Two ideas that make hard optimization work

How the load-balancing loss keeps Mixture-of-Experts models from collapsing — and how coding agents solve olympiad math by letting Lean grade their proofs.

Prepared for Daniel 2026 · LLM learnings
Part 1 — Mixture of Experts

The load-balancing loss

Where it's computed, what it's added to, how it's built, and why the exact form works.

1.1The problem it solves

An MoE layer replaces a dense feed-forward block. A small router (gating network) looks at each token and picks the top-k of N experts to process it. Only those experts run — that's the whole point: sparse compute, huge parameter count, cheap forward pass.

The failure mode is routing collapse. Early in training a few experts get slightly better, the router sends them more tokens, they improve faster, the router sends them even more. A rich-get-richer loop. You end up with a handful of experts doing all the work and the rest as dead weight — you paid for capacity you never use, and the per-expert capacity buffers overflow (dropped tokens).

The load-balancing loss is a regularizer that fights this collapse.

1.2Setup and notation

For a batch of T tokens and N experts, the router produces a logit hi(x) per expert, then a softmax:

pi(x) = ehi(x) NΣj=1 ehj(x)

pi(x) is the router's soft probability of sending token x to expert i. The actual routing is the hard top-k (Switch Transformer uses k = 1). Now define two per-expert quantities over the batch:

fi = 1T Σx 𝟙{ token x routed to i } Pi = 1T Σx pi(x)

fi is the hard load — a histogram built from argmax (counts). Pi is the soft load — the average router probability. Hold onto that distinction; the whole trick rides on it.

1.3The loss

The Switch Transformer / GShard auxiliary loss:

ℒaux = α · N · NΣi=1 fi Pi
  • N scales it so the minimum value is 1 regardless of expert count — this makes α transferable across model sizes.
  • α is a small coefficient, typically ~10-2: big enough to enforce balance, small enough not to drown the language-modeling objective.

1.4Where it's computed and what it's added to

It is computed inside every MoE layer (each layer has its own router, so its own f, P), summed over all MoE layers, and added to the main next-token cross-entropy loss as a single scalar:

ℒtotal = ℒCE + α layers ℓΣ ℒaux(ℓ)

Direct answer to your question

It is not attached to a "final layer." It's a global auxiliary term added to the overall training loss. Every router in the network receives a gradient from it. Backprop of ℒCE teaches "route tokens to experts that predict well"; backprop of ℒaux teaches "and spread the load evenly." They're summed and optimized jointly.

1.5Why the form Σ fi Pi — the key trick

This is the part most explanations skip. You'd want to minimize imbalance directly — say, the variance of fi. But fi comes from an argmax: it's a non-differentiable count. No gradient flows through it. You cannot train the router by pushing on fi.

Pi, by contrast, is a smooth softmax average — fully differentiable. The product fiPi resolves the tension:

  • fi acts as a non-differentiable weight — "how overloaded is expert i right now."
  • Pi carries the gradient — it's the knob the router can actually turn.

Take the gradient with respect to the router's soft mass:

∂ ℒaux ∂ Pi = α N fi

Read it literally: the downward push on expert i's router probability is proportional to how overloaded it is. Overloaded experts (fi large) get their routing probability suppressed hard; starved experts (fi ≈ 0) get almost no penalty, so the router is free to send them more. Exactly the corrective signal you want — and it's differentiable because it lands on Pi.

1.6Why the minimum is a balanced state

Both f and P are distributions on the simplex (Σfi = 1, ΣPi ≈ 1). The loss is a dot product ⟨f, P⟩ of two probability vectors. Subject to those constraints, it is minimized when both are uniform, fi = Pi = 1/N:

N NΣi=1 1N · 1N = N · N · 1N2 = 1 (the minimum)

Intuition

The dot product of two distributions is largest when both are spiky and aligned on the same experts (that's collapse), and smallest when both are flat. So minimizing this one scalar literally is pushing the router toward uniform utilization.

1.7Two companions you'll see in practice

Router z-loss (ST-MoE) keeps the router logits from blowing up — numerical stability and sharper routing:

ℒz = 1T Σx ( log NΣi=1 ehi(x) )2

It penalizes a large log-sum-exp, i.e. large logits, and is added with its own small coefficient.

Auxiliary-loss-free balancing (DeepSeek-V3) — the newer trend. Instead of adding ℒaux (which slightly hurts quality by fighting the LM objective), add a per-expert bias bi to the score used for top-k selection:

select top-k of  ( hi(x) + bi )

The bias is not trained by gradients — a simple control rule nudges it after each step: if expert i was overloaded, decrease bi; if starved, increase it. You get balance without ever perturbing the main-loss gradient. Frontier MoE models lean this way now because the classic aux loss imposes a small "balance tax" on quality.

Part 2 — Formal math agents

Solving math with Lean verification

How OpenAI/DeepMind-style agents turn olympiad proofs into a search problem with a perfect referee.

2.1What Lean gives you: a verifier that can't be fooled

Lean is an interactive theorem prover. Math is written in its dependent type theory, where a deep correspondence (Curry–Howard) holds:

a proof  ≡  a term a theorem  ≡  that term's type

Proving "√2 is irrational" means constructing a term whose type is the formal statement. A tiny, trusted kernel then type-checks that term. If it checks and contains no sorry (placeholder), the theorem is true — modulo trusting the kernel, which is a few thousand lines and heavily audited.

Why this matters for LLMs

You get a binary, mechanical, zero-false-positive reward signal. The proof compiles or it doesn't. No human grader, no "looks plausible," no reward-hacking a fuzzy judge. Compare informal math (an AIME-style numeric answer), where the only check is did the final number match — the reasoning in between can be nonsense and still land right. Lean verifies the entire chain.

2.2The pipeline

  1. Autoformalization. An LLM translates the natural-language problem into a formal Lean theorem statement — the goal to be closed. This step is itself error-prone and a research problem: a wrong formalization means you prove the wrong thing.
  2. Proof generation as a REPL loop. The agent doesn't emit a whole proof blind. Lean exposes a proof state (current goal + hypotheses). The model proposes a tactic — a step like induction n or rw [lemma] — Lean executes it and returns the new state: either subgoals, or an error.
  3. Search over the tactic tree. Each proof state is a node; each candidate tactic is an edge to a child state. The model is a policy (propose promising tactics) and often a value (how close is this state to done?). Run best-first search or MCTS; the kernel prunes invalid branches instantly, so the search never wanders into false territory.
  4. Error feedback. A failed tactic returns a specific message ("unification failed", "unknown identifier"). The agent conditions on it and revises — the same debugging loop a coding agent runs against a compiler or failing test.
state0 —tactic₁→ state1 —tactic₂→ … → QED (no goals left)

Environments like LeanDojo expose exactly this loop programmatically so an agent can drive it.

2.3Why it works: RL with verifiable rewards

The verifier is what makes reinforcement learning tractable. The reward is just:

R(proof) = 1 if the Lean kernel accepts (no sorry),  0 otherwise

Because reward is free and exact, you can run expert iteration / self-play — the AlphaProof recipe:

  1. Take a large corpus of problems, auto-formalized into Lean (AlphaProof did this on the order of a million).
  2. Let the current model attempt them, searching for proofs.
  3. Keep every proof Lean verifies. These become new gold training data — no human labeling needed.
  4. Fine-tune on the verified proofs → stronger model → harder problems fall → more verified proofs. Loop.

This bootstraps unlimited, guaranteed-correct training data — the scarce resource in math. It's the AlphaZero pattern: a perfect, cheap referee lets the system generate its own curriculum.

2.4Landmarks worth knowing

  • AlphaProof (DeepMind, 2024) — Lean-based, expert-iteration RL; reached IMO silver-medal level. At test time it even generates and trains on variants of the target problem.
  • DeepSeek-Prover (V1.5 / V2) — open models trained with Lean feedback and tree search.
  • miniF2F — the standard benchmark of formalized olympiad problems.
  • Mathlib — Lean's vast library of formalized math; the lemma database tactics draw on.

The one-sentence intuition

For fuzzy tasks an LLM's own confidence is the only signal, and it hallucinates. Lean replaces that with a kernel that mechanically certifies correctness — so even a sloppy, hallucination-prone generator becomes trustworthy, because only kernel-verified proofs survive, and that same certificate doubles as a perfect reward for training the generator to get better.

Part 3 — The tools & the "Alpha" lineage

LeanDojo, AlphaProof, AlphaZero, AlphaEvolve

What each one actually is, where it came from, and how they're related (and where they're not).

3.1LeanDojo — the environment that makes Lean drivable

Lean on its own is an interactive tool for humans typing at an editor. To let a program attempt proofs, you need an API that loads a theorem, feeds it tactics, and hands back the resulting state. That's LeanDojo — an open-source toolkit and benchmark from a Caltech-led group (2023).

It does three distinct jobs:

  1. Tracing / data extraction. It parses Lean + Mathlib and pulls out every proof as structured (proof state → tactic → next state) triples, plus which library lemmas ("premises") each step used. This turns the entire Mathlib corpus into supervised training data.
  2. An interaction gym. A Gym-style environment: reset to a theorem, run_tac(state, tactic), observe the new goal or an error. This is exactly the REPL loop from Part 2 — LeanDojo is what exposes it programmatically so an agent (or a search algorithm) can drive Lean in a reproducible sandbox.
  3. A benchmark + a baseline prover. It ships the "LeanDojo Benchmark" and ReProver, a retrieval-augmented model: before generating a tactic it retrieves likely-relevant lemmas from Mathlib (there are hundreds of thousands), which sidesteps the model having to memorize the whole library.

In one line

LeanDojo is the plumbing: it converts Lean from a human editor into a machine-drivable environment with training data and a benchmark. It is infrastructure, not a champion solver — the thing research systems are built on top of.

3.2AlphaZero — the ancestor idea (2017)

Before the math systems, the template. AlphaZero (DeepMind, 2017) mastered Go, chess, and shogi from scratch — no human games, only the rules. Its recipe is the thing every later "Alpha" system reuses:

  • A single neural net outputs a policy (which moves look promising) and a value (how good is this position).
  • That net guides a tree search (Monte-Carlo Tree Search) instead of brute force.
  • Training is pure self-play: play games against itself, and — crucially — the rules of the game are a perfect referee that says who won. That ground-truth outcome is the reward.

Lineage: AlphaGo (2016, learned from human games) → AlphaGo Zero (2017, self-play, Go only) → AlphaZero (2017, one algorithm for three games) → MuZero (2019, learns the rules too).

The reusable insight

Learned policy/value + search + a perfect automatic referee lets a system bootstrap superhuman skill with zero human labels. Now swap the "game": if you have a perfect referee for proofs, you can play the same game with math.

3.3AlphaProof — AlphaZero, but the game is theorem-proving (2024)

AlphaProof (DeepMind, 2024) is the direct descendant that made the swap. Its architecture maps one-to-one onto AlphaZero:

The mapping

Game position → a Lean proof state.  Legal moves → tactics.  Policy/value net → a language model (built on Gemini) proposing and scoring tactics.  The perfect referee (game rules) → the Lean kernel.  Self-play → attempting a huge bank of problems and keeping the verified proofs.

Concretely it works in two stages: a formalizer network auto-translates ~1 million natural-language problems into Lean statements, then a solver searches for proofs, trained by AlphaZero-style reinforcement learning against Lean's yes/no verdict. At test time it does something striking — it generates variations of the target problem and tries to prove those too, a self-reinforcing loop that sharpens it on the specific question in front of it.

Result: at IMO 2024 it solved 3 of the 6 problems (paired with AlphaGeometry 2 for the geometry one), scoring 28/42 — silver-medal level, one point below gold. Every answer was a Lean-verified proof.

So, related to AlphaZero?

Yes — directly. AlphaProof is the AlphaZero recipe with the Lean kernel playing the role the game rules played in Go. Same self-play + search + learned policy/value, different referee.

3.4AlphaEvolve — a cousin, not a sibling (2025)

AlphaEvolve (DeepMind, 2025) is where people get confused. It shares the family DNA — an LLM in a loop with an automatic evaluator — but it is a different method for a different job.

It's an evolutionary coding agent: Gemini proposes edits to a program, an automatic evaluator scores each candidate, the best survive and get mutated further — genetic programming with an LLM as the mutation operator. It descends from DeepMind's earlier FunSearch (2023). It doesn't prove theorems; it evolves algorithms and code for any problem you can score automatically.

What it found: a way to multiply two 4×4 matrices with 48 multiplications (beating Strassen's 49 from 1969), improved bounds on open math problems (e.g. the kissing number in 11 dimensions), and real Google infrastructure wins — data-center scheduling, TPU circuit tweaks, and a ~23% speedup of a Gemini training kernel.

How the three relate

All descend from the same idea AlphaZero crystallized: a generator (search/LLM) + an automatic ground-truth evaluator, in a loop. They differ in the generator and the evaluator:

Bottom line on the relationships

AlphaProof ↔ AlphaZero: same algorithm family, direct descendant. AlphaProof ↔ AlphaEvolve: cousins — same "LLM + auto-verifier loop" philosophy and the same "Alpha" lab, but different techniques (RL proof-search vs. evolutionary code-search) and different domains. LeanDojo sits underneath the math branch as the environment, not a competitor to any of them.

The common thread

Why these belong in one document

Every system here turns an intractable optimization into a workable one by manufacturing the right signal. MoE conjures a differentiable balance signal (fiPi) out of a non-differentiable count. Lean conjures an exact, verifiable reward out of otherwise-ungradeable reasoning. And the Alpha family shows the payoff at scale: once you have a cheap, perfect referee, a generator can bootstrap its own superhuman training data. In every case, the cheap-but-precise signal is the whole game.

The agent harness — how to build the machine around the model

A model that can call tools is not yet an agent. The harness is the software system that turns raw model calls into a reliable autonomous worker — the loop that keeps it going, the tool interface it acts through, the context it reasons over, the sandbox that keeps it safe, and the tests that tell you it actually worked. This is the general version — the machine behind Claude Code, OpenCode, SWE-agent and their kin — component by component, each defined before it is used, every choice labelled build-this or skip-this, and every borrowed term explained in plain English first.

For Daniel · companion to the Hedge-Fund Harness notes · grounded in Claude Code, OpenCode, SWE-agent, OpenHands, Aider + the agent-scaffold literature · read top to bottom · ~40 min

Start here · what "the agent harness" means

The harness is the machine around the model

A chat model answers one prompt. An agent pursues a goal across dozens of steps, touching a real environment. Everything between "one model call" and "a trustworthy autonomous worker" is the harness. Let's define it once, precisely, before building any of it.

▸ Definition — the agent harness

An agent harness (also called the scaffold or the agent-computer interface) is everything around the model weights that lets the model act: the loop that calls the model and runs what it asks; the tools it acts through; the context assembled into each call; the sandbox and permissions that bound its power; the verification that feeds real results back; and the memory, tracing and evaluation that make runs durable and measurable. The model is the engine; the harness is the car, the road, the dashboard, and the driving test.

▸ In plain English

Imagine a brilliant new hire who can reason about anything but has no hands, no memory between meetings, and no idea what's safe to touch. The harness gives them hands (tools), a desk with only the right papers on it (context), a rule about which drawers need a manager's sign-off (permissions), a way to check their own work before calling it done (verification), and a notebook that survives to tomorrow (memory). Same hire — but now the work is bankable. Without the harness you just have a clever opinion that can't do anything and can't be trusted when it tries.

◆ The one line to remember

The interface beats the model. The single most-cited finding in this whole area (SWE-agent, Princeton) is that redesigning the interface a fixed model acts through moves its success rate more than most model upgrades do — their edit-tool and linter guardrail swung SWE-bench resolve rate by 3–8 points with the same weights. The corollary: agent capability you measure is always harness × model, never the model alone. A weak harness makes a strong model look dumb, and a strong harness is where a small, disciplined team can actually win.

§Workflow or agent? Don't reach for autonomy by default

Anthropic's Building Effective Agents draws the line worth drawing first. A workflow is LLM calls wired together on predefined code paths — you know the steps in advance. An agent is an LLM that dynamically directs its own tool use in a loop, for problems where "it's difficult or impossible to predict the required number of steps." Autonomy is a cost-and-risk knob, not a badge: use the simplest thing that works, and only climb to a full loop when the task is genuinely open-ended.

▸ The failure this prevents

The classic way an agent project dies: you wire up the exciting part (model + a big pile of tools + a loop) first, watch a demo succeed once, and only later discover it loops forever on the second task, silently "believes" it fixed a bug it never re-tested, floods its own context until it forgets the goal, or runs rm -rf because nothing gated the shell. Every one of those is a harness bug, not a model bug — and each has a component below whose whole job is to prevent it.

Component 1 · the controller

The agent loop — think, act, observe, repeat

The beating heart is almost embarrassingly simple: a while loop. Its difficulty is entirely in the stop condition and in making sure every turn is anchored to reality.

▸ Definition — the agent loop

The agent loop is the controller that (1) calls the model, (2) executes whatever tools the model requested, (3) appends the results to the conversation, and (4) calls the model again — repeating until the model returns an answer with no tool calls, or a budget/stop condition fires. This is the ReAct pattern (Yao et al., 2022): interleave reasoning ("thought") with acting (a tool call) and observing (the result) in one trajectory. Claude Code frames the same three beats as gather context → take action → verify results, chained across dozens of steps.

gather context→ call model (think)→ run tool (act)→ read result (observe)→ verify / progress? └────────── no answer yet → loop back to think ──────────┘ 
# The entire agent, minus the cleverness
messages = [system_prompt, user_goal]
while True:
    reply = model(messages, tools)          # think
    if not reply.tool_calls:               # stop condition: model is done
        return reply.text
    for call in reply.tool_calls:          # act
        result = run(call)                  # ← real environment, ground truth
        messages.append(observation(result))# observe
    if steps++ > MAX or budget_exceeded(): # the OTHER stop condition
        return escalate_to_human()
▸ In plain English — the one rule that makes it work

Every turn, the agent must gain ground truth from the environment — the actual tool result, the actual test output — not its own guess about what happened. The loop is a feedback controller: it only converges if it can see the error between "what I intended" and "what actually happened." An agent that acts and then assumes success has opened the loop, and open loops drift.

▸ Good

"Fix the failing tests" → run the suite → read the errors → search the source → edit → re-run the suite → stop when green. A real stop condition (tests pass) and a budget cap with a human-escalation exit if it stalls.

▸ Bad

A hardcoded 5-step pipeline for an open-ended task (too rigid), or a loop with no environment feedback where the model declares victory without re-running anything (never converges), or no cap at all (runaway cost, "compounding errors").

▸ Design rule

Give the loop two stop conditions: a success condition read from the environment (tests green, goal state reached) and a safety condition (max steps / token budget / wall-clock) that escalates to a human instead of spinning. And prefer a workflow over a loop whenever you can actually predict the steps — the loop is for when you can't.

Component 2 · the interface — the load-bearing one

The tool interface — the verbs you hand the model

If you get one component right, make it this one. The evidence that interface design beats model size is the strongest single result in the field.

▸ Definition — the Agent-Computer Interface (ACI)

The ACI (SWE-agent, Princeton, NeurIPS 2024) is the purpose-built set of commands and feedback a model acts through — the agent's equivalent of a human's GUI. The thesis: LLM agents are a new category of end user, and just as a good UI makes a person more capable without making them smarter, a good ACI makes a fixed model dramatically more capable. Design tools for the model: few and high-impact, clearly named, returning readable context, with actionable errors and a token budget.

▸ The numbers — interface moves the score at fixed model

SWE-agent's ablation on SWE-bench Lite (same model throughout) is the receipt everyone cites:

ConfigurationResolve rateΔ
Full ACI18.0%—
Remove the edit-linter guardrail15.0%−3.0
Full-file view instead of a 100-line window12.7%−5.3
Shrink viewer window 100 → 30 lines14.3%−3.7
Remove the custom edit tool (raw editing)10.3%−7.7

A 7.7-point swing from the edit tool alone — larger than many model upgrades — with the weights held fixed. Aider's parallel result: switching GPT-4 Turbo to a rigid unified-diff edit format cut "lazy coding" ~3× and lifted its benchmark from 20% → 61%.

2.1The five rules of a good tool

  • ✓Few, high-impact, consolidated — not thin API wrappers. One search_contacts beats making the agent chain list_users → list_events → filter and burn context doing your join for you.
  • ✓Namespace them. asana_search, gdrive_search — so related tools cluster and the model picks the right one.
  • ✓Return meaning, not opaque IDs. Give back "Jane Smith / #eng-team", not a raw UUID. Anthropic found resolving UUIDs to human-readable names "significantly improves precision."
  • ✓Make errors actionable. "File not found — did you mean src/app.py? Use an absolute path." not a bare stack trace. The error message is a prompt back to the model.
  • ✓Budget the output. Claude Code caps a single tool response at ~25,000 tokens by default — a huge grep gets truncated with a note, not allowed to blow the window.
▸ Poka-yoke — make mistakes impossible, don't just warn against them

The Japanese manufacturing term for "mistake-proofing." If the agent keeps passing relative paths that break, don't add a warning to the docstring — change the tool signature to require an absolute path so the wrong call can't be expressed. Anthropic fixed a whole class of pathing errors this way. The best tool interface makes the correct action the only representable one.

▸ The failure this prevents

Too many overlapping tools "distract agents from pursuing efficient strategies"; opaque IDs and cryptic tracebacks cause failed retrievals and unrecoverable loops; whole-file edits invite lazy "// rest unchanged" rewrites. Anthropic reports that small refinements to tool descriptions alone pushed Sonnet to state-of-the-art on SWE-bench Verified — this is the highest-leverage tuning surface in the harness.

Component 3 · what the model sees

Context management — the finite attention budget

The context window is not free storage you fill up. It is a budget that degrades as it fills, and managing it well is most of what separates a coherent long run from a confused one.

▸ Definition — context engineering & context rot

Context engineering (Anthropic) is choosing the smallest set of high-signal tokens to put in each call. Its central hazard is context rot: "as the number of tokens in the context window increases, the model's ability to accurately recall information decreases." A related, older finding is lost in the middle (Liu et al., 2023): models use information best at the start or end of the context and degrade sharply when it sits in the middle — even in long-context models. A bigger window does not buy uniform recall.

3.1The four levers, lightest touch first

  • 1Clear old tool outputs. The cheapest win — a 40k-token file dump from step 3 is dead weight by step 20. Drop it first.
  • 2Compact / summarize. Near the limit, summarize the conversation so far — preserving "architectural decisions, unresolved bugs, and implementation details" — and reinitialize on the summary. Claude Code does this automatically (/compact).
  • 3Retrieve just-in-time. Hold lightweight identifiers (file paths, queries, links) and fetch the content only when needed, instead of pre-loading everything up front.
  • 4Offload to memory. Write durable state to a notes file outside the window (see §7), so the window stays a working set, not an archive.

▸ Good

Persistent rules live in a CLAUDE.md file (reloaded every call), not in fragile chat history. MCP tool definitions load on demand so only names cost tokens until used. Critical instructions sit at the edges of the prompt where recall is best.

▸ Bad

Dumping a whole repo or a 200k-token file into the prompt up front. The window refills the instant it's summarized — "compaction thrash" — and the agent forgets the goal it was given in the middle of a wall of retrieved text.

▸ System-prompt altitude

Anthropic's "Goldilocks" rule: a system prompt should be neither brittle hardcoded logic nor vague hand-waving, but "specific enough to guide behavior, flexible enough to give strong heuristics," organized with clear section headers. Start minimal; add a rule only when you've seen the failure it fixes.

Component 4 · scaling out — carefully

Sub-agents & orchestration — power at 15× the cost

One agent, one context window. When a task is too broad for one window, you fan out — but this is the most expensive lever in the harness, and it helps only for the right shape of work.

▸ Definition — orchestrator–workers

In the orchestrator–workers pattern (Anthropic), a lead agent decomposes the task and spawns sub-agents, each in its own isolated context window, each returning only a "condensed, distilled summary" (~1–2k tokens) rather than its full transcript. The point is context isolation: five parallel explorations don't pollute the lead's window; it sees five clean summaries. The subtasks are decided by the orchestrator at run time, not predefined.

▸ The numbers — worth it, but only sometimes

From Anthropic's multi-agent research system:

  • ✓A lead + sub-agents beat a single agent by 90.2% on their research eval.
  • ✕It burned ~15× the tokens of a plain chat.
  • ✓Token usage alone explained ~80% of the performance variance — much of the win is just "more tokens spent searching in parallel."
▸ Fan out when…

The work is broad and parallelizable and each strand is independent: researching many sources, searching a large codebase from several angles, reviewing a diff along several dimensions at once. Isolation helps and the strands don't need each other's intermediate state.

▸ Stay single-agent when…

The work is tightly interdependent — most coding, where edit B depends on what edit A just did. Anthropic is explicit: multi-agent is "less effective for tightly interdependent tasks such as coding." Fanning those out means agents step on each other and you pay 15× for a worse result.

▸ Design rule

Reach for sub-agents only when outcome value dominates token cost and the task decomposes into independent, breadth-heavy strands. Keep each worker's return small (a summary, not a transcript), and never fan out interdependent edits. Autonomy scales cost super-linearly — spend it where isolation actually buys you something.

Component 5 · the safety cage · build EARLY

Permissions & sandboxing — least privilege by default

The moment an agent can run a shell command, it can also delete your work or leak your secrets. This component is what lets you widen the leash later without dread — so it comes early, not last.

▸ Definition — the safety cage

Two layers. Permissions decide which actions need a human's sign-off: side-effecting or irreversible actions (writes, shell, network, deploys) are gated behind approval modes and allowlists, with least privilege as the default. Sandboxing decides where code runs: inside an isolated container/VM with scoped filesystem and network access, so arbitrary code can't harm the host. Permissions bound intent; the sandbox bounds blast radius.

5.1Permission modes — a graduated leash

Claude Code's four modes (cycled with Shift+Tab) are a clean template for graduated autonomy:

ModeWhat it allowsUse when
PlanRead-only exploration; no source edits at allUnderstanding a codebase before touching it
ManualAsk before every edit and every shell commandUnfamiliar or high-stakes territory
Accept editsAuto-approve file writes + benign fs commands; still ask for the restA trusted, well-scoped task in progress
AutoA lightweight classifier LLM reviews each action and blocks risky ones in the backgroundLong autonomous runs where prompting on every step is impractical

Trusted commands (npm test, git status) go on an allowlist in settings, scoped org → project → personal, so the routine stuff stops asking while the dangerous stuff still gates.

▸ Good

Every action runs in a per-session Docker sandbox (OpenHands does exactly this — arbitrary code "can be run safely without risking the host"). Reversible edits get a checkpoint before each write so the human can rewind; irreversible actions (DB writes, deploys, external APIs) always require explicit approval.

▸ Bad

Full auto-approve (bypassPermissions) on a machine with production credentials and no sandbox. One prompt-injection in a fetched web page or a mis-parsed instruction and the agent runs rm -rf or exfiltrates a token — with nothing between intent and damage.

▸ Design rule — and its honest limit

Default to least privilege and make the safe path the easy one (allowlists beat approval fatigue; a background classifier beats a blanket "yes"). But note the boundary: checkpoints can rewind local files — they cannot un-send an email or un-drop a table. Route anything with an external, irreversible effect through stricter, explicit human approval, always.

Component 6 · closing the loop

Verification — wire actions to ground truth

This is the component that turns §1's open loop into a closed one. Without it the agent is guessing whether it succeeded; with it, the environment tells it — and rejects bad actions before they land.

▸ Definition — the feedback loop

Verification connects the agent's actions to real environment signals — tests, linters, type-checkers, compilers — and forces the agent to observe the result before proceeding. The strongest form is a guardrail that rejects a bad action at the interface rather than letting it commit and cascade. A close cousin is the evaluator–optimizer loop (Anthropic): one model call generates, another critiques against explicit criteria, and it iterates — worth it "when we have clear evaluation criteria and iterative refinement provides measurable value."

▸ The exemplar — SWE-agent's pre-apply linter

When the agent edits a file, the edit tool runs a linter before the change is written: "Python files will be checked for syntax errors after the edit. If an error is found, the edit will not be executed" — and the tool shows the error, the proposed change, and the original so the agent can recover. That one guardrail is worth 3 points of resolve rate (18.0% → 15.0% without it). The action is rejected at the interface; the broken state never exists.

▸ Good

Edit → type-checker/linter runs → agent reads any error and fixes it → tests run → agent reads the result → only then declares done. Reflexion-style (Shinn et al.): on failure, the agent writes a short natural-language self-critique and retries with it in context.

▸ Bad

Apply a diff blind and move on. The build breaks and the agent never learns — it carries a false "done" into the next step, and the error compounds. "It looks right" is not verification; running it is.

▸ Design rule

Prefer guardrails that make a bad action impossible to commit over post-hoc detection. Every action the agent takes should produce an observable, machine-checkable signal — and the loop should be structured so the agent must read that signal before its next move. A harness with no verification is a very expensive way to generate confident wrong answers.

Component 7 · durable state

Memory & persistence — a notebook that survives the window

Context (§3) is working memory and it gets wiped by compaction. Real long-horizon work needs state that outlives any single window — and runs you can reproduce, resume, and fork.

▸ Definition — memory, three tiers

Scratchpad / notes: files the agent writes to and reads back, "persisted to memory outside of the context window," enabling strategies impossible when everything must fit in one window. Project memory: instructions and conventions loaded into every session (a CLAUDE.md / rules file). Session persistence: an append-only log of the run so it can be resumed, forked, and reproduced. The reference architecture for long-term recall is Generative Agents' memory stream — store timestamped observations, retrieve by recency × importance × relevance, periodically reflect into higher-level notes.

▸ Good

Durable rules live in CLAUDE.md (loaded into every system prompt), not in chat that compaction will drop. Sessions are written to JSONL so --continue, --resume and --fork-session work. OpenHands makes an append-only event log the state — "what the agent perceives is a fold over that log" — so every run is exactly reproducible.

▸ Bad

Relying on conversation history for anything that must persist. Claude Code warns early instructions "can get lost" in compaction — so a rule you stated once in turn 2 is gone by turn 40. Durable facts belong in a file, not in the transcript.

▸ Design rule

Anything that must survive a compaction or a restart lives on disk, not in context. Make the log the source of truth (state = a fold over events) and you get reproducibility, resume, and fork for free — the same discipline that makes a backtest trustworthy makes an agent run trustworthy.

Component 8 · the instruments

Observability & evaluation — measure the harness, not the model

You cannot improve what you cannot see, and you cannot trust a number that measured the wrong thing. This component makes every run legible and grades the whole harness honestly.

▸ Definition — traces & agentic evals

Observability: every action and observation is logged, with accumulated tokens and cost, so a run can be audited step by step (OpenHands' typed event stream is this — the audit log is the state). Agentic evaluation: grading the harness on tasks that require the loop, tools and environment end-to-end — not the base model on multiple-choice quizzes, which miss everything the harness does.

▸ Track tokens as a first-class metric

Because token usage explained ~80% of performance variance in Anthropic's multi-agent evals, cost is not just a budget line — it's a capability signal. Log tokens per run alongside success rate, or you'll ship a harness that "improved" only by quietly spending 15× more.

▸ Good

A trace per run (actions, observations, cost); the harness graded on SWE-bench Verified / Terminal-Bench with resolve@1 reported honestly; and per-component eval — Anthropic even lets agents "analyze your results and improve your tools for you."

▸ Bad

Grading the base model on a knowledge quiz and inferring agent capability. SWE-agent showed the interface alone moves resolve rate 3–8 points at fixed model — a static eval attributes harness bugs to the model and misses every real regression.

The frontier · the harness that designs itself

The meta-harness — treating the scaffold as a searchable artifact

Everything above is hand-authored. A research lineage asks the next question: if the scaffold matters this much, why design it by hand at all?

▸ Definition — automated design of agentic systems

The insight behind ADAS (Hu, Lu & Clune, 2024): if agents are defined in code — prompts, tool wiring, control flow — then the harness itself is a searchable design space, not a fixed thing you author once. Their Meta Agent Search has a meta-agent program new agents against a growing archive of prior designs; the invented scaffolds beat hand-designed ones and transfer across domains and models.

▸ The lineage — search → self-edit → evolve
  • ›ADAS / Meta Agent Search (arXiv:2408.08435) — search over agents-as-code; discovered scaffolds beat hand-built ones.
  • ›Gödel Agent (arXiv:2410.04444) — an agent that reads and rewrites its own code at runtime toward a high-level objective. The purest "meta harness" — and a research prototype, not production.
  • ›Darwin-Gödel Machine (arXiv:2505.22954) — self-modifies and empirically validates each change on a benchmark; self-improved from 20.0% → 50.0% on SWE-bench. Verification (§6) becomes the engine of self-improvement.
▸ Why this belongs in a harness doc

Two reasons. First, it is the strongest evidence for this document's thesis — DGM's 20%→50% swing came entirely from changing the scaffold, model fixed. Second, it clarifies the goal: a great harness is not a pile of features but a design space you can measure and move through. You may build it by hand for years — but knowing it's searchable changes how you build it: instrument everything (§8), and every component becomes a knob you can tune with evidence instead of taste.

Putting it together

Build order — a runnable spine before a wide leash

Run-time order (§1→§8) is not build order. Build the parts that let you trust and observe an agent before the parts that make it powerful. Here's a sensible sequence.

Step 1days
Loop + 2–3 tools + a sandbox. The while loop (§1), a read tool, an edit tool and a run-command tool (§2) — all executing inside a container (§5) from the very first line. Never run a tool loop un-sandboxed, even in a prototype.
Step 2days
Verification + tracing. Wire tests/linter feedback into the loop (§6) and log every action with its cost (§8). Now you can see what the agent does and whether it worked — before you trust it with anything.
Step 3week
Permission modes + the ACI polish. Add graduated permission modes and an allowlist (§5), then invest hard in tool ergonomics (§2) — names, readable returns, actionable errors, output budgets. This is where the biggest score gains hide.
Step 4week
Context management + memory. Add compaction, just-in-time retrieval (§3) and a CLAUDE.md + session log (§7). This is what turns a 10-step demo into a 100-step worker.
Step 5ongoing
Benchmark, then (maybe) fan out. Grade the whole harness on SWE-bench Verified / Terminal-Bench (§8). Only once a single agent is solid and measured do you add sub-agents (§4) — and only for breadth-heavy work worth 15× the tokens.
◆ The ordering principle

Observability and safety before autonomy. Verification, tracing and the permission cage come before you widen the leash, because they're what let you extend it without fear. A powerful agent you can't observe or contain is a liability; a modest one you can trust and measure is a foundation you can keep building on. Same lesson as any serious research system: the discipline is the moat, not the raw capability.
